## 1. 产品定位与用户场景

**痛点**：零基础中文学法语者看到生词（`maison`、`agneau`）只认识字母、不会读，想开口却没底气；现有词卡有读音信息但无系统规则，只能一词一听，无法举一反三。

**定位**：一套**融入式、可边用边学**的读音规则体系（39 条核心规则），嵌在生词卡、对话消息、阅读生词旁——用户不离开当前场景，点一下就能"听规则、看示范、跟着读、记进度"。

**融入式（非 Tab）的价值**：不新增第 5 Tab、不打断现有 4 Tab 心智，把学习成本藏在"好奇点一下"里，符合"像婴儿一样自然轻松"。**读音是"随身小抄"，不是"第五门课"。**

| 时机 | 行为 |
|---|---|
| 用户主动点生词卡/阅读标注/对话法语词 | 展开读音入口（用户触发，不弹窗打断） |
| 对话进行中（用户输入/录音） | **不主动弹**，零干扰 |
| 首次遇到含生词页面 | 一次性温和引导气泡，可关闭、仅一次 |
| 跟读反馈后 | 不连续弹窗；用户自选"再来一次"或关闭 |

**可发现性三保险**（无 Tab 必须解决"用户怎么知道能学读音"）：
1. **首次提示**：第一次进入含生词页面，一次性气泡"生词旁有个小喇叭，点一下能听标准读音、还能跟着读～"（可关、仅一次）
2. **侧栏常驻**：小册子入口固定在词卡侧栏，随时可见可进
3. **空态引导**：一条未学时显示"从最常用的 ai / au 开始，三条就好～"，给低门槛起点

## 3. 学习闭环（四步）

| 步骤 | 交互 | 文案口径 |
|---|---|---|
| 1 规则讲解卡 | 规则说明 + 2–3 例词 + 🔊 标准示范（现有 TTS） | "这条规则是～先听一遍"；"再听一次也可以" |
| 2 🎙 跟读 | 录音跟读例词/短句，走独立 ASR 链路（借鉴 `transcribeExamAudio()`，不误发聊天流） | "轮到你啦，慢慢读～" |
| 3 温和反馈 | 近似比对后三档反馈（见 §4），并可回看标准示范 | 见 §4；**不准绝不说"错了"** |
| 4 掌握度记录 | 按"见过→学过→能自己读"累积（见 §5） | "记下啦，这条你越来越熟了～" |

**闭环红线**：全程"可以/慢慢来/再试一次就好"；跟读不准一律归因于"再听一遍示范/收音小问题"，绝不归因于用户能力。

## 4. 跟读反馈：产品语义 + 技术实现（关键难点）

### 4.1 为什么不能精确打分（产品约束，有实证）
`QA_ASR_CONTEXT_AB.md` 证明临界区近音词会被 ASR 误识别（froid→foudre、café→enquêter），错词 100% 时任何上下文都救不回。故 **ASR 转写 ≠ 用户真实发音**，反馈必须假设"ASR 可能听错用户"，宁可高估、绝不误伤。产品只约束"近似 + 从宽 + 不判错"。

### 4.2 三档温和反馈话术（PM，无精确分数）
| 档 | 触发（产品语义） | 反馈话术 |
|---|---|---|
| A 很像 | 近似匹配度高 | "听起来很接近啦，这个音你拿捏得不错～" |
| B 接近了 | 大体接近、个别音可更饱满 | "差不多啦，中间那个音可以再饱满一点，再听一遍示范就好～" |
| C 没听清/兜底 | ASR 无结果、明显误识别、匹配度低 | "这次没太听清，可能是收音的小问题，我们再来一次～" 或 "想再听一遍示范吗？" |

**自评兜底**：用户可主动点"我觉得读对了"自评掌握；掌握度由"接触次数 + 多次尝试 + 自评"累积，**不由单次 ASR 决定**；C 档永远给"再来一次"而非"读错了"。

### 4.3 ASR 比对管线（架构师技术方案，字段【待冻结】）

**★跟读目标与示范文本分离（架构师修订我原稿缺陷）**：规则 JSON 中 `audio_text` 只作"听"的示范（法语例词串，直接喂 `/api/tts`），**不作比对目标**；比对目标取独立字段 `shadow_text_fr`，比对单元由 `shadow_mode ∈ syllable/word/phrase` 决定（单音→词→词组渐进）。流程：先听 `audio_text` 示范 → 再跟读 `shadow_text_fr` 短单元。

复用 `POST /api/asr/transcribe` 的 `raw_text / corrected / confidence / low_confidence`：跟读请求带 `hints`（目标词及同规则例词，用现有 `buildAsrHints()`）+ `context`（目标词所在短句，用 `buildAsrContext()`）做偏置，提升转写准确率。评分函数 `score(target, asr)` 的 **target 取 `shadow_text_fr`**（不再是 audio_text 或 word）。收到转写后按下列判据**按序短路**判定。

### 档位判据定稿（架构师修订 2，覆盖此前所有档位描述，以此为准）

**关键语义边界**：`BAND_UNSURE` = **系统侧不确定**（不是用户读错）；其余档位是"系统较可信时对读音的评价"。二者文案口径必须分开。

| 档位 | 判据（按序短路） | 反馈语义（称呼/文案以 PM 为准） |
|---|---|---|
| `BAND_UNSURE` | ASR 低置信 / 音频 <2s / 目标词查不到词典且字符串近似也不够 | 归因为"没听清/太短"，回显自评或重录，**不判错、不归咎用户** |
| `BAND_EXACT` | 归一化后字符串相等 | 达标，肯定 |
| `BAND_CLOSE` | 字符串相似度 ≥ R_HIGH | 很接近了 |
| `BAND_CLOSE_SOUND` | 音素编辑距离=0（同音词/拼法差异），或距离 1 且落在易混等价集 | 读得挺像，再顺一下就好；**此项不占 BAND_UNSURE** |
| `BAND_RETRY` | 音素距离 ≥2 且不属易混集 | 温和"再试一次"，**不判错、不打红叉** |
| 降级 | ASR 服务不可用 / 空音频 / 50001 | 不评分，可跳过，绝不中断学习流 |

> 阈值 R_HIGH / CONF_FLOOR / 音素距离容忍度均【待冻结】，先用默认值由 QA 调。与 content 建议的差异已由架构师说明并取得一致：content 曾建议"距离 1 落易混集 → BAND_UNSURE 上限"，改判为 `BAND_CLOSE_SOUND`，以保证"系统没听清"与"读得挺像"两种情形文案不混。

### 音素层：从"可选"升级为全量开启（content 已配齐 156 个 IPA 槽位）

- `phonetic?: string`（宽式 IPA，斜杠包裹、音节用 `.` 分隔，如 `/mɛ.zɔ̃/`），schema 保留可选标记，但 content 已 39 条 × 4 例词 = 156 槽位全部配齐，实际**全量可用**。
- **词典无需新增文件/字段/content 返工**：前端加载 `pronunciation_rules.json` 时遍历 `examples[].phonetic` 在内存自建 `word_fr → IPA` Map 供查表，零额外 IO。
- ASR small 出的是正字法文本（如 `maison`）而非 IPA，比对前：目标词与用户转写词都查 Map 取 IPA → 归一化（去 `/` 与音节点 `.`、忽略大小写重音）→ 只留音素序列做编辑距离。
- **易混等价集**（视为 0 距离或低权重）：`/ɛ̃/≈/œ̃/`、`/e/≈/ɛ/`、`/ø/≈/œ/`、`/ʁ/` 各实现视为同一音位、词尾 `/j/≈/i/`；un 的 `/œ̃/ ~ /ɛ̃/` 并存直接进等价集。
- **词末静音规则组（第 7 组）是音素门控最大价值点**：正字法有 s/t/d 而目标 IPA 无对应辅音，用 IPA 比对天然规避"拼对但读多"的误判。
- 查不到词典的词 → 退化为字符串近似兜底，不崩；ASR 错认变体（maison→mézon）本轮不预枚举，放 P2 按真实数据积累。

**总指挥裁决——技术六档 → 用户可见三档映射（防两份契约分裂）**：技术内部六档判据，用户**永远只看 PM 定的三档话术**（过多分级会造成压力，违背低情感过滤）。映射如下，任何文档不得另起称呼：

| 技术档位 | 用户可见档（§4.2） | 用户看到的话术 |
|---|---|---|
| `BAND_EXACT` / `BAND_CLOSE` / `BAND_CLOSE_SOUND` | A 很像 / B 接近了 | "听起来很接近啦…" / "差不多啦，中间那个音可以再饱满一点…" |
| `BAND_RETRY` | C 再来一次（读得不够像） | "想再听一遍示范吗？" |
| `BAND_UNSURE` / 降级 | C 没听清（系统侧不确定） | "这次没太听清，可能是收音的小问题，我们再来一次～" |

**比对实现位置**：纯前端函数（接收 `{target=shadow_text_fr, ASR 结果, IPA Map}` → `{band, 反馈话术}`），无网络、无状态、可直接单测；服务端不做评分，只提供 ASR 转写能力。

**已知边界（诚实标注）**：白名单自评纠偏（A/B 档可让用户"我还想再试"）；C 档始终对用户有利；**不追求声学发音评分**（需音素级强制对齐，超出本项目范围），本方案是"转写文本近似比对 + IPA 音素近似"，不是发音评测。

## 6. 内容方案（内容角色，39 条核心规则）

### 6.1 分组与数量（已核对：4+6+7+6+5+4+4+3 = 39；starter 19 + core 20 = 39）

| 分组 | 条数 | 代表规则 |
|---|---|---|
| A 字母表与读音概念 | 4 | 字母名称 vs 音、h 不发音、c 的软硬、g 的软硬 |
| B 基础元音 | 6 | a/ɑ/、e 的四种符号、i/y、o、u、è/ê 与 é |
| C 基础辅音 | 7 | qu=/k/、gu=/g/、ch=/ʃ/、gn=/ɲ/、ph=/f/、th=/t/、r 小舌音 |
| D 元音字母组合 | 6 | **ai/ay=/ɛ/**、**au/eau=/o/**、**ou=/u/**、**oi=/wa/**、eu/œu=/ø/、ei=/ɛ/ |
| E 辅音字母组合 | 5 | -er 词尾、tion=/sjɔ̃/、ss、cc、x 的两种读音 |
| F 鼻化元音 | 4 | an/en、in/ien、on、un/um |
| G 词末辅音规则 | 4 | 词末辅音一般不发音、词末 -e、联诵、连音 |
| H 高频例外与易错 | 3 | **词末 -e 不是总读/ə/**、**h 与嘘音 h**、同位语与数字特殊读法 |

**starter 19 条**：A 全组 + B 基础元音 + D 中 ai/au/ou/oi + C 的 ch/qu/gn + a/e/i/o/u 单音跟读，覆盖约 70% 常见词拼读。
**core 20 条**：其余组合、鼻化元音、词末规则与例外，进阶到能拼读较长词。

### 6.2 中文学习者三大易错点（teaching tip）
1. **词末辅音不发音**（maison 的 s、chat 的 t）——中文习惯逐字母读，必须单独强调
2. **鼻化元音 an/en/in/on**——中文无对应音，易读成"安/恩"，要提示气流从鼻腔走、不要加鼻音 n 的收尾
3. **ou / au 混淆**——ou=/u/（如 `oui`），au=/o/（如 `aujourd'hui`），用对比例词强化

### 6.3 跟读文本长度建议（适配 ASR small）
- 单音跟读（如 a、é）：适合"熟悉口型"，但 ASR 对过短音频识别不稳 → 只作示范口型练习，**不进入比对评分**
- 单词跟读（2–8 字母，如 `maison`、`chat`）：主力跟读单位，进入比对
- 短词组（3–5 词，如 `un petit chat`）：进阶跟读，进入比对
- 避免整句长文本（ASR 误识别率高，与"从宽不判错"冲突）

### 6.4 规则条目 schema【架构师与 content 已对齐，字段名以此为准】
> 以下字段名来自 content 实际产出并经架构师确认，非总指挥初稿——实现时逐字照此，不得改用 `word`/`highlight`/`read_aloud` 等旧名。

```json
{
  "id": "ph_comb_02",
  "group": "元音字母组合",
  "title": "ai / ay 读 /ɛ/",
  "description_zh": "字母组合 ai 和 ay 通常读 /ɛ/，嘴巴张开、舌头放平，像短促的『哎』。",
  "examples": [
    { "word_fr": "maison", "meaning_zh": "房子", "note_zh": "ai 在词中读 /ɛ/", "phonetic": "/mɛ.zɔ̃/" },
    { "word_fr": "chaise", "meaning_zh": "椅子", "note_zh": "同样的 ai 音", "phonetic": "/ʃɛz/" }
  ],
  "audio_text": "maison, chaise, lait",
  "shadow_text_fr": "maison",
  "shadow_mode": "word",
  "tier": "starter",
  "tags": ["D组", "元音组合"]
}
```
- **id 格式**：`ph_<group>_<nn>`（分组编号 + 序号），content 全 39 条统一
- **听/跟读分离**：`audio_text` 只喂 TTS 作示范；跟读比对目标取 `shadow_text_fr`，单元由 `shadow_mode ∈ syllable/word/phrase` 决定
- **phonetic**：宽式 IPA、斜杠包裹、音节用 `.` 分隔；schema 标可选但 content 已全量配齐 39×4=156 槽位
- **注意（总指挥校准 2026-11-18）**：架构师终裁确认 `/ɑ̃/` 为全库统一写法（鼻化元音 an/en/am 等），**不是笔误、不进易混等价集**，content 早期「改成 /ɑ/」的说法作废；落 JSON 时一律保留 `/ɑ̃/`。`/ɑ/`（如 `pâte` 的 â）与 `/ɑ̃/` 是两个不同音位，不得混写。
- 39 条均含：中文描述、2–4 例词（法词/中文释义/规则体现/音标）、TTS 朗读文本、跟读文本与模式、难度层级
- 内容边界：读音规则属通用语言知识；例词为常用词，不照搬 `texts.json` 整句，无"官方真题"风险

## 7. 技术方案（架构师交付，字段【待冻结】）

### 7.1 数据模型
- **规则内容**：新 JSON `data/input/pronunciation_rules.json`（39 条，随 `data/input/` 现有模式；启动加载 + 进程内缓存），不建内容表——规则是静态教学数据，与 texts/assessment/exam 一致放 JSON。
- **掌握度**：新表 `pronunciation_progress`（§5.1）；与 `word_cards.pronunciation` **不冲突**——后者是词卡自带音标展示，前者是规则级掌握追踪，数据粒度不同，互不覆盖。
- 所有新查询带 `user_id`，为多用户演进铺路（延续 UX 方案裁决）。

### 7.2 端点草图【待冻结】
| 方法 | 路径 | 语义 |
|---|---|---|

### 7.3 前端状态设计（无 Tab 的碎片化触发）
- 规则数据**一次加载、进程内缓存**（39 条静态数据），三个融入点共享，不重复请求。
- 一个轻量浮层组件承载规则卡（讲解+例词+🔊+🎙+反馈），从词卡/阅读/对话气泡三处调用同一组件。
- 跟读录音**必须复用独立链路 `transcribeExamAudio()` 模式**（自建 MediaRecorder → 直连 `/api/asr/transcribe` → 只回填浮层输入框），**绝不调用 `transcribeAudio()`**（会误发聊天流）。
- 对比对算法做纯函数封装，便于单测。

### 7.4 零回归与风险
- 现有 21 端点/users 表/GLM/ASR 链路不动；`requirements.txt` 仍两行。
- 隐私：跟读音频不留存（ASR 端已 unlink），不存原始转写文本。
- 性能：39 条规则 JSON 启动缓存，无运行时 IO。
- 一致性：并入「我的成长」时同源读取、不重复记录。
- **本轮不做**：独立 Tab、声学发音评分（音素强制对齐）、多用户账号、FSRS。
